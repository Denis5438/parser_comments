## 1. Введение и цели аудита

Настоящий аудит представляет собой экспертное исследование исходного кода Telegram-бота для проведения розыгрышей и конкурсов (`giveaway-contest-bot`), написанного на TypeScript с использованием фреймворка **grammY** и библиотеки **ExcelJS**. Бот выполняет выгрузку комментариев из четырех платформ (**YouTube**, **ВКонтакте**, **Дзен**, **Instagram**), фильтрует участников по кодовым словам и правилам дедупликации, формирует детализированные `.xlsx`-отчеты и выбирает победителя с помощью рандомайзера.

**Цели аудита:**
1. Выявить все потенциальные дефекты логики, уязвимости безопасности (включая CWE-1236 и инъекции сущностей Telegram HTML), архитектурные узкие места и риски отказа в обслуживании (DoS/OOM).
2. Оценить корректность обработки протоколов и API сторонних платформ (лимиты, пагинация, рекурсивные ветки ответов, антиспам-эвристики).
3. Проанализировать сохранность сессионных данных и поведение системы в многопользовательской конкурентной среде.
4. Предоставить исчерпывающие инженерные рекомендации по исправлению каждого дефекта с готовыми фрагментами кода.
5. Обеспечить строгую сохранность существующей кодовой базы без внесения несанкционированных изменений.

### Детальная методология по компонентам:

1. **Шаг 1: `src/services/vkLimiter.ts` (Рейт-лимитер и очередь VK API)**

   - *Фокус проверок:* Утечка слотов параллелизма (`activeRequests`), блокировка очереди при `catch (sleep)`, поведение Circuit Breaker при коде 6 (`TOO_MANY`), полнота классификации фатальных и повторных ошибок в `isRetryableError`.

2. **Шаг 2: `src/services/vk.ts` (Парсер ВКонтакте)**

   - *Фокус проверок:* Обработка пустых страниц и условие выхода из цикла, учет флага `item.deleted`, выгрузка вложенных веток (`threads`), фильтрация плоских ответов (`reply_to_comment`) при `includeReplies: false`.

3. **Шаг 3: `src/services/youtube.ts` (Парсер YouTube)**
   - *Методология:* Анализ парсинга Video ID, разбора ответов MWEB Innertube API и официального Google API v3.
   - *Фокус проверок:* Подавление ошибок в блоке `catch (err) { if (comments.length > 0) break; }`, генерация фиктивных меток времени `new Date()`, зацикливание при повторе continuation token, обработка слэшей в `/shorts/`.

4. **Шаг 4: `src/services/dzen.ts` (Парсер Дзен)**
   - *Методология:* Проверка резолвинга `documentId` и `publicationPublisherId` через HTML-скрейпинг и fallback-регулярки.
   - *Фокус проверок:* Коллизия channel ID и document ID в URL `dzen.ru/id/...`, отсутствие пауз между сетевыми вызовами (риск Captcha/429), тихое прерывание пагинации при сбоях.

5. **Шаг 5: `src/services/instagram.ts` (Парсер Instagram)**
   - *Методология:* Проверка преобразования shortcode в `mediaId`, заголовков Web API (`X-IG-App-ID`), сессионных куки.
   - *Фокус проверок:* Регулярное выражение shortcode (поддержка `/reels/`), глубина выгрузки дочерних комментариев (`child_comments`), рассинхронизация курсоров `min_id` против `max_id`.

6. **Шаг 6: `src/bot.ts` (Интерфейс Telegram и сессионный конечный автомат)**
   - *Методология:* Анализ промежуточного слоя grammY, обработчиков текстовых сообщений и callback-кнопок.
   - *Фокус проверок:* Экранирование пользовательских данных в HTML (`parse_mode: 'HTML'`), лимит длины сообщения 4096 символов, состояние гонки при параллельной отправке команд во время сбора (`isScraping`), изоляция групповых чатов, криптографическая стойкость PRNG.

7. **Шаг 7: `src/services/healthServer.ts` (Health-сервер мониторинга)**
   - *Методология:* Проверка реализации встроенного HTTP-сервера Node.js, соответствия стандартам RFC 7231 (GET vs HEAD).
   - *Фокус проверок:* Асинхронность привязки порта (состояние гонки `server.listen`), реакция на ошибки `EADDRINUSE`/`EACCES`, точность статуса `/health` относительно работы long-polling Telegram-бота.

8. **Шаг 8: `src/services/deduplicator.ts` (Дедупликация и нормализация)**
   - *Методология:* Исследование функции `cleanText`, хронологической сортировки и классификации участников.
   - *Фокус проверок:* Набор знаков препинания (дефисы, кавычки, многоточия), поддержка Unicode-эмодзи, нормализация `ё/е`, жадность подстрочного поиска в режиме `contains`, достоверность текста причины в `DuplicateRecord`.

9. **Шаг 9: `src/services/excel.ts` (Генератор Excel-отчетов)**
   - *Методология:* Анализ построения книги через библиотеку `ExcelJS`, форматирования ячеек и генерации колонок.
   - *Фокус проверок:* Уязвимость формульной инъекции (CWE-1236), потребление оперативной памяти (V8 Heap DOM vs Streaming Writer), спецсимволы в именах листов, невалидные управляющие символы XML 1.0, лимит 32 767 символов на ячейку.

10. **Шаг 10: `src/services/cleanupService.ts` (Служба очистки файлов)**
    - *Методология:* Проверка работы фонового интервала, логики фильтрации файлов и обработки ошибок файловой системы.

11. **Шаг 11: `src/index.ts` и `src/config.ts` (Жизненный цикл процесса)**

## 3. Всесторонний аудит логики и граничных случаев (R2)

### 3.1. Сетевые вызовы, таймауты, блокировки и обработка ошибок платформ

1. **Тихое усечение результатов сбора (Silent Data Truncation)**:
   В трех из четырех парсеров платформ (`youtube.ts:319-324`, `dzen.ts:253-258`, `instagram.ts:146-150`) обнаружен одинаковый антипаттерн обработки исключений в цикле пагинации:
   ```typescript
   catch (err: any) {
     if (comments.length > 0) {
       break; // Тихо прерываем цикл и возвращаем то, что успели собрать!
     }
     throw new Error(...);
   }
   ```
   **Механизм катастрофического сбоя:** Если парсер успешно выгрузил первые 100 комментариев из 5 000, а на 101-м комментарии произошел разрыв TCP-соединения (`ECONNRESET`), таймаут сокета (`ETIMEDOUT`) или временная блокировка платформы по IP (HTTP 429), цикл тихо завершается. Telegram-бот не получает никакого сигнала об ошибке и переходит к дедупликации и выбору победителя. В результате **более 95% участников конкурса оказываются отсеяны без ведома организатора**, что делает розыгрыш нелегитимным и дискредитирует владельца канала.

2. **Сетевые ошибки и недостаточная классификация в `vkLimiter.ts`**:
   Метод `isRetryableError` (`vkLimiter.ts:164–198`) проверяет только внутренние коды ошибок VK 6, 9, 10 и строковые коды `ETIMEDOUT`, `ECONNRESET`, `EAI_AGAIN`. При этом полностью игнорируются:
   - Временный сетевой сбой `ENOTFOUND` (сбой DNS-резолвера, часто случающийся в контейнерах Docker/Render).
   - Внутренняя ошибка платформы VK 1 (`Unknown error occurred`).
   - Стандартные HTTP 502 Bad Gateway / 503 Service Unavailable / 504 Gateway Timeout от прокси-балансировщиков VK.
   При возникновении любой из этих штатных временных ошибок задача мгновенно завершается фатальным сбоем вместо экспоненциального повтора.

3. **Отсутствие троттлинга запросов в Дзен (`dzen.ts`)**:
   В `dzen.ts` корневые комментарии и дочерние ветки опрашиваются подряд в цикле `for` без каких-либо задержек (`sleep/delay`). При выгрузке публикаций с сотнями веток отправка 50–100 HTTP-запросов за пару секунд гарантированно вызывает срабатывание системы защиты SmartCaptcha от Яндекс/Дзен, возвращающей HTTP 403 / HTML-форму капчи.

### 3.2. Корректность пагинации и обработка древовидных веток комментариев

1. **YouTube: Бесконечный цикл и ложное преждевременное завершение (`youtube.ts`)**:
   - *Бесконечный цикл:* В цикле MWEB Innertube токен пагинации извлекается из ответа. Если YouTube по какой-либо причине вернет тот же самый токен продолжения (штатное поведение при некоторых фильтрах комментариев), а массив `foundInBatch > 0`, цикл `while (hasMore)` превращается в бесконечный цикл, выкачивая одни и те же комментарии до исчерпания памяти процесса.
   - *Ложный обрыв:* Условие `if (!continuationToken || foundInBatch === 0) hasMore = false;` (строка 316) останавливает сбор, если в очередной порции `foundInBatch === 0`. Однако в протоколе Innertube батч может содержать только элементы метаданных (заголовки, смену сортировки) и новый токен продолжения без комментариев. Сбор обрывается на середине ветки.

2. **ВКонтакте: Падение на видеозаписях и пропуск веток (`vk.ts`)**:
   - В блоке `video.getComments` (строки 196–233) отсутствует проверка `if (!response.items || response.items.length === 0) break;`. Если у видео отключены комментарии или достигнут конец списка, а VK возвращает пустой ответ, код не завершает цикл или пытается итерировать `undefined`, выбрасывая `TypeError`.
   - В `video.getComments` вообще не реализована выгрузка ответов на комментарии к видео (в отличие от постов на стене).
   - В блоке `wall.getComments` (строки 142–170) опрос ветки ответов через `vkLimiter.execute` не обернут в локальный `try...catch`. Если хотя бы один родительский комментарий был удален модератором прямо во время работы скрапера, запрос ветки падает с ошибкой, что приводит к аварийному падению всего сбора поста.

3. **Instagram: Потеря глубоких веток ответов и блокировка пагинации (`instagram.ts`)**:
   - Строки 121–135 извлекают только массив предпросмотра `item.child_comments` (содержит максимум 2–3 комментария). Настоящие вложенные ответы, которых может быть сотни, требуют отдельного запроса к эндпоинту `api/v1/media/${mediaId}/comments/${item.pk}/child_comments/`, который парсером не вызывается.
   - Строки 142–145 опираются исключительно на `next_min_id`. Для реверсивной пагинации Instagram часто возвращает курсор `next_max_id`. Если `next_min_id` равен `null`, пагинация завершается после первой же страницы (20 комментариев).

### 3.3. Граничные случаи (Edge Cases) и условия гонки (Race Conditions)

1. **Коллапс мьютекса параллелизма в `vkLimiter.ts` (Critical Race Condition)**:
   Архитектурный анализ метода `execute()` (`vkLimiter.ts:206–252`):
   ```typescript
   while (true) {
     await this.acquireToken();
     this.activeRequests++; // [A] Захват слота
     try {
       return await fn();
     } catch (error: any) {
       // ... вычисление actualWait ...
       await new Promise((resolve) => setTimeout(resolve, actualWait)); // [B] Сон ДО finally!
     } finally {
       this.activeRequests--; // [C] Освобождение слота
       this.processQueue();   // [D] Запуск следующей задачи из очереди
     }
   }
   ```
   **Сценарий развития гонки:**
   - Пусть `maxConcurrent = 1`. Задача 1 начинает выполнение.
   - Задача 1 получает ошибку 6 (`TOO_MANY`) от VK и входит в блок `catch`.
   - В точке `[B]` Задача 1 засыпает на `actualWait` (от 1.2 до 13 секунд).
   - **В течение всего сна `this.activeRequests === 1`**. Очередь заблокирована, другие запросы не могут стартовать.
   - Сон завершается, управление переходит в блок `finally`.
   - В точке `[C]` `this.activeRequests` уменьшается до `0`, а в точке `[D]` вызывается `processQueue()`, который немедленно будит Задачу 2 из очереди.
   - **ОДНОВРЕМЕННО С ЭТИМ** Задача 1 не выходит из метода, а делает следующую итерацию `while(true)` и в точке `[A]` моментально вызывает `acquireToken()`.
   - В результате **и Задача 1 (повтор), и Задача 2 начинают выполняться параллельно**, полностью нарушая ограничение `maxConcurrent: 1` и отправляя пачку параллельных запросов к VK API, что моментально вызывает бан по лимитам.
   - *Эмпирическое подтверждение:* Специальный стресс-скрипт зафиксировал всплеск `activeRequests` до 2 и 3 при лимите 1.

2. **Состояние гонки в методе `acquireToken()` (`vkLimiter.ts:90–105`)**:
   Условие `canDispatchImmediately` проверяет `this.activeRequests < this.maxConcurrent`, декрементирует токены (`this.tokens--`), но **не увеличивает** `this.activeRequests`. Увеличение `this.activeRequests++` происходит только в вызывающем коде `execute()` на строке 208. Если два асинхронных вызова приходят в одном тике событийного цикла (Event Loop), оба видят `activeRequests = 0` и оба диспетчеризуются синхронно, вызывая всплеск параллелизма.

3. **Состояние гонки привязки порта в `src/services/healthServer.ts`**:
   Функция `startHealthServer(port)` является синхронной и возвращает объект `server` до того, как сетевой сокет физически перейдет в состояние `LISTENING` (событие `'listening'`).
   *Подтверждение дефекта:* Запуск встроенного теста `npm test` завершается ошибкой:

4. **Гонка двойного клика в Telegram (`src/bot.ts:594–627`)**:
   Обработчик нажатия на кнопку `pick_random_winner` не содержит флага защиты от повторного клика (debouncing/mutex). При быстром двойном тапе пользователем Telegram отсылает два идентичных callback-запроса, и бот отправляет в чат два разных сообщения с двумя разными победителями конкурса.

### 3.4. Сохранность сессий, утечки памяти (OOM) и жизненный цикл процесса

1. **Уязвимость к отказу в обслуживании по памяти (Heap OOM) в `src/bot.ts`**:
   - Переменная `sessions = new Map<number, UserSession>()` (`src/bot.ts:30`) объявлена на уровне модуля без каких-либо механизмов очистки по времени жизни (TTL), ограничений на максимальный размер (LRU-кэш) или сброса на диск.
   - На строке 502 объект сессии сохраняет `session.lastResult = deduplicationResult`, который включает в себя полный массив сырых комментариев со всеми дубликатами и текстами.

2. **Перезапись сессии и рассинхронизация во время активного сбора**:
   - В `src/bot.ts:154-162` при получении текстового сообщения с ссылкой бот создает новую сессию: `sessions.set(ctx.chat.id, newSession)` без проверки того, выполняется ли в данный момент сбор по предыдущей ссылке (`session.isScraping === true`).
   - Если пользователь отправил ссылку A, начался сбор на 3 минуты, а через минуту пользователь отправил ссылку B, объект сессии ссылки A уничтожается. Завершившийся через 2 минуты фоновый сбор A запишет результат в устаревшую или чужую сессию. При нажатии пользователем кнопки выбора победителя бот выдаст ошибку "Сессия устарела".

3. **Коллизия контекстов в групповых чатах (`src/bot.ts`)**:
   Ключом в `sessions` выступает `ctx.chat.id`. В коде отсутствует проверка `ctx.chat.type === 'private'`. Если добавить бота в группу или супергруппу, все участники группы начинают делить одну общую сессию. Любой участник группы может нажать кнопку смены режима или отправить ссылку, перетерев настройки администратора.

4. **Отсутствие глобальных перехватчиков фатальных ошибок в `src/index.ts`**:

Любое необработанное отклонение промиса в фоновых задачах (например, в таймере очистки файлов или сетевом сокете) в современных версиях Node.js приводит к немедленному аварийному завершению всего процесса.

### 3.5. Дедупликация участников, проверка кодовых слов и генератор случайных чисел (PRNG)

1. **Неполная очистка текста и отказ в участии честным пользователям (`deduplicator.ts:14–19`)**:
   Функция `cleanText` использует следующее регулярное выражение для обрезки знаков препинания:
   `/^[\s!?,.:;«»"'—–\(\)\[\]{}#*~`]+|[\s!?,.:;«»"'—–\(\)\[\]{}#*~`]+$/gu`
   **Критические дефекты нормализации:**
   - В наборе символов **отсутствует стандартный ASCII-дефис `-` (U+002D)**, слэш `/`, обратный слэш `\`, знак плюс `+`, знак равенства `=`, символ многоточия `…` (U+2026), а также типографские кавычки `“ ” ‘ ’`.
   - В конкурсах с кодовым словом `+` (самый популярный формат в Telegram/VK) комментарий `+` будет принят, но комментарий `- участвую -` или `участвую…` будет отклонен в строгом режиме, так как многоточие или дефис не будут удалены!
   - Не удаляются эмодзи на границах слов (например, `🎉 Участвую! 🎉`).
   - Не применяется Unicode-нормализация (`normalize('NFKC')`) и не заменяется буква `ё` на `е`. Если организатор задал слово `елка`, а участник написал `ёлка`, участник будет исключен.

2. **Ложные срабатывания в режиме `contains` (`deduplicator.ts:98–102`)**:
   В мягком режиме совпадение проверяется через `lower.includes(k)`. Без проверки границ слов (`word boundaries`) короткие кодовые слова вызывают массовые ложные включения. Например, кодовое слово `дар` включит комментарии со словами *"благодарен"*, *"подарок"*, *"удар"*; слово `кот` включит *"бойкот"*; слово `win` включит *"window"*.

3. **Искажение причины исключения и двойной учет в отчетах (`deduplicator.ts:135–158`)**:
   - В режиме `first_wins`, если участник написал сначала невалидный комментарий (в 10:00: *"Привет всем"*), а затем комментарий с кодовым словом (в 10:05: *"Участвую"*), участник попадает в список валидных участников по второму комментарию. Но в таблицу исключенных дубликатов на строке 152 записывается строка:
     `Оставлено 2 коммент. (учтен только 1-й, остальные 1 отсеяны)`.
     Это утверждение является **ложным**: 1-й комментарий был отсеян, а учтен был как раз 2-й.
   - Пользователь оказывается одновременно и в массиве `participants`, и в массиве `duplicates`. Итоговое сообщение бота суммирует обе длины, вводя организатора в заблуждение по поводу баланса комментариев.

4. **Небезопасный генератор случайных чисел победителя (`src/bot.ts:602`)**:
   Выбор победителя реализован как:
   `const randomIndex = Math.floor(Math.random() * participants.length);`
   `Math.random()` использует некриптографический псевдослучайный генератор xorshift128+. Его внутреннее состояние детерминировано и может быть предсказано при знании предыдущих значений в процессе. В коммерческих розыгрышах с ценными призами (автомобили, смартфоны, денежные суммы) это ставит под сомнение юридическую честность конкурса.

### 3.6. Генерация Excel-отчетов (CWE-1236, RAM, лимиты OpenXML) и автоочистка файлов

1. **Уязвимость к формульной инъекции в электронных таблицах (CWE-1236 / CSV Injection)**:
   В файле `src/services/excel.ts` (строки 66–74 и 138–145) имена пользователей (`username`), тексты комментариев (`commentText`) и история повторов (`commentsHistory`) записываются напрямую в ячейки без санитизации:

     number: participant.number,
     username: participant.username,

4. **Риск потери данных службой очистки (`src/services/cleanupService.ts`)**:

### Группа 1: Парсеры и управление сетевыми лимитами (Scrapers & Rate Limiter)

#### ДЕФЕКТ №1.1: Нарушение мьютекса параллелизма и утечка слотов в рейт-лимитере VK
- **Файл и строки:** `src/services/vkLimiter.ts:206–252`
- **Критичность:** **Critical** 🔴
- **Описание проблемы:** В методе `execute` блок `try...catch...finally` помещен внутрь бесконечного цикла `while(true)`. При получении повторной ошибки (например, VK code 6 `TOO_MANY`) ожидание `setTimeout(actualWait)` выполняется в блоке `catch` **до вызова `finally`**. На протяжении всего сна счетчик `activeRequests` удерживает значение 1. При выходе из `catch` блок `finally` декрементирует `activeRequests` и вызывает `processQueue()`, что запускает следующую задачу из очереди, а текущая задача сразу же начинает повторную попытку на строке 207. Это приводит к параллельному выполнению нескольких задач вразрез с настройкой `maxConcurrent: 1`.
- **Сценарий воспроизведения:** Запустить две параллельные операции выгрузки из VK. При возникновении первой ошибки 6 обе задачи переходят в параллельное исполнение, вызывая лавинообразные блокировки со стороны VK API.
- **Технические рекомендации:** Вынести удержание параллелизма исключительно на фазу вызова `fn()`, а фазу сна выполнять без удержания слота:
```typescript
// Рекомендуемое исправление в src/services/vkLimiter.ts
public async execute<T>(fn: () => Promise<T>, taskName: string = 'VK API Request'): Promise<T> {
  let attempt = 0;
  while (true) {
    await this.acquireToken();
    let result: T;
    let hasResult = false;
    let thrownError: any = null;

    this.activeRequests++;
    try {
      result = await fn();
      hasResult = true;
    } catch (error: any) {
      thrownError = error;
    } finally {
      this.activeRequests--;
      this.processQueue();
    }

    if (hasResult) {
      return result!;
    }

    attempt++;
    const code = thrownError.code || thrownError.error_code;
    if (code === 6 || code === 'TOO_MANY') {
      this.pausedUntil = Math.max(this.pausedUntil, Date.now() + this.circuitBreakerPauseMs);
    }

    if (attempt > this.maxRetries || !this.isRetryableError(thrownError)) {
      throw thrownError;
    }

    const exponentialDelay = this.baseDelayMs * Math.pow(2, attempt - 1);
    const jitter = Math.floor(Math.random() * 400);
    const totalDelay = Math.min(this.maxDelayMs, exponentialDelay + jitter);
    const actualWait = (code === 6 || code === 'TOO_MANY' ? 1000 : 0) + totalDelay;

    await new Promise((resolve) => setTimeout(resolve, actualWait));
  }
}
```
